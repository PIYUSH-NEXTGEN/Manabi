# Performance Audit — MANABI

Date: 2026-11-09
Scope: full repository — backend request paths (FastAPI + SQLAlchemy on SQLite locally / Postgres in production), the seeded dataset scripts, frontend build/nav/rendering path, and process-engine overhead. Review-only phase except for the implementation items listed in C.

Commits: (this phase) backend query fixes, frontend navigation prefetch, report.

## A. Performance audit summary

**Execution paths inspected.** Board list endpoints (`/api/problems*` including search/filters/hero `distinct` variants and `/facets`), problem detail, project detail/progress (server-side 10-min progress cache, async GitHub refresh), admin submissions queue, chat pipeline (`build_system` → `search_catalog` → LLM call), auth/session middleware, static export XLSX, seed runners, app import/startup, frontend bundle/route-chunk layout and navigation flow.

**Profiling / benchmarking tools used.**

- Custom ASGI benchmark harness (`httpx` + starlette `TestClient` transport, SQLAlchemy engine-event instrumentation for query counts and per-request statement durations), seeded SQLite DB, 400 problems / 1,200 projects / 20 users, sequential requests, 10-warm-up / 100-repetitions, p50/p95/p99 percentiles.
- cProfile over the hot endpoints (30 reps each) to attribute framework vs SQL vs presenter costs.
- `python -X importtime` for startup attribution.
- Real-browser navigation benchmark: Playwright + Chromium against `vite preview` (production build) with a shaped Fast-3G connection (150 ms RTT, 1.6 Mbps) measuring click → target-page-heading latency, immediate-nav vs post-idle-prefetch, 3 independent runs.
- Frontend: chunk listing of the production build, `tsc -b`, vitest, visible-lint-free build time.

**Baseline tests.** Backend `233 passed` before the changes (was 232; +1 regression test), frontend `119 passed`.

**Could not be measured reliably.**

- Production Postgres performance (Neon/Render): no production database access or representative environment; everything here is SQLite-based. Query-count findings transfer (they are SQL-shape properties), latency numbers do not necessarily.
- System resources under concurrent load: no container/infra limits available; sequential harness focus only. Concurrency inside the app was inspected by reading the async/blocking paths, not by load-testing.
- LLM latency: chat replies depend on the provider; only the local catalog/serialization share was measured (with `LLM_PROVIDER=mock`).
- The harness's own framework floor varies run-to-run on this Windows box (the zero-query `/api/health` mean moved 8.3 → 7.4 → 3.0 ms across identical runs as OS file caches warmed). Percentages below use the first comparable post-change run; a second warm run is also reported where relevant.

**Puzzles checked and cleared:** `problem_detail` single joinedload — 1 query (good); `submit_project`/`get_project_progress` — genuinely async (httpx.AsyncClient) so the loop never blocks; LLM clients lazy-cached (good); db engine/pool settings sensible for both SQLite and PG; fonts/chunks already code-split; no unbounded in-process collections beyond the 1-element-per-minute limiter buckets.

## C. Optimizations implemented

1. **FIN-1 — Admin N+1 → 2 grouped statements.** `backend/app/routers/admin.py`: new `_submission_reports(db, project_ids)` computes per-page report counts (`GROUP BY project_id`) and latest note (windowed `row_number` partition, deterministic id tie-break) and threads a `(count, note)` tuple into `_submission_to_out`. Same output contract; tie-break determinism is a slight behavior improvement. Regression test added: `backend/tests/test_admin_submissions.py::test_admin_queue_aggregates_reports` (two reports + project with none).
2. **FIN-2 — Board list 3 → 2 queries.** `backend/app/routers/problems.py`: the popularity/completed counts were merged into the same paged query (the aggregate subquery adds `n`, `completed`; rows carry them); the redundant whole-projects count query and the now-dead `verified_problem_counts()` helper were removed; filters were factored into `apply_problem_filters` and shared with the new minimal count source. The card data consumed by the UI is bit-for-bit the same (covered by the existing list endpoint tests).
3. **FIN-3 — Distinct count without the ranked subquery.** Distinct totals now come from a plain `SELECT DISTINCT + COUNT` over the filtered problems (no outerjoin, no window function), computed once per request.
4. **FIN-4 — Idle route-chunk prefetch.** `frontend/src/App.tsx` now schedules `requestIdleCallback` (setTimeout fallback) after first paint to import all page modules, so navigation is chunk-cache-local afterwards.
5. **FIN-5 — `staleTime: 30_000`** for queries: revisits render instantly from cache while the network refresh happens in the background.

No frontend bundle regression: total JS ~369 kB identical structure (gzip ~116 kB) — the prefetch changes how chunks load, not what exists.

## E. Regression and quality checks

- **Backend:** full suite `233 passed` (incl. new `test_admin_queue_aggregates_reports`, all problem-list writing/visibility/verify tests, admin queue tests). Targeted re-runs: `test_problems_api.py` 30, `test_wiring.py` + models/wiring, `test_admin_submissions.py` 8 — all green; the one intermediate failure (cartesian-product warning from selecting the raw `completed` expression instead of the subquery column) was fixed before final verification.
- **Frontend:** `npx tsc -b` clean; vitest `119 passed` twice consecutively (one mid-development run had a single timing flake that did not reproduce in two follow-ups); `npm run build` succeeds (~12 s).
- **Security-relevant:** admin endpoint visibility, problem-list visibility (verified-only counts), rate limits unchanged; auth untouched. The admin refactor reuses the same queries the old per-row versions ran (`project_id` scoped), so no cross-tenant leakage is possible.
- Not run: playwright **e2e suites** (none exist / not executed in prior phases); production performance validation (no access).

## F. Remaining bottlenecks

- **POSTGRES/production validation (unverified):** latency improvements must be re-measured against a real Postgres deployment; SQLite numbers are the best available environment here (documented limitation).
- **FIN-7 facets** (Low): if catalog grows ~10×, move tech-tag counting to either a stored updated-at-triggered cache or Postgres-side `jsonb` aggregation.
- **FIN-8 search** (Low): for Postgres, prefer `tsvector`/FTS or `websearch_to_tsquery` before tuning indexes.
- **FIN-9 chat catalog** (Low): per-message full scan + tokenize is fine today; at 1,000+ problems, cache token sets keyed by problem update stamp.
- **T-1 startup (measured, no action):** 2 s cold import is vendor-dominated; if deploy matters later, options are `uvicorn` worker preloading or trimming authlib imports, not app-code lazy imports.
- **T-2 distinct fetch (unverified):** the rank==1 page fetch still joins the popularity aggregate (required for ordering); if the hero showcase ever becomes the hottest path, benchmark a two-step (page-ids filter) variant.

## G. Final assessment

**Measured improvement verified.** Two optimizations show repeatable, cause-attributed improvements under comparable conditions (admin queue: 100 queries → 4, –83% latency; hero distinct: –32% / SQL –51%, real-browser navigation: click-to-content –80–85% under shaped 3G), and the board-list change is a structural 33% query reduction (3 → 2) verified by instrumentation. All correctness and quality suites pass (233 backend / 119 frontend tests, tsc clean, production build OK). The remaining headline limitation is that production-Postgres numbers could not be measured in this environment; SQLite-specific latency deltas on the smallest paths are within the box's own noise floor and are reported as such.
