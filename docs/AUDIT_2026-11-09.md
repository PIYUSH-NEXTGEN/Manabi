## B. Findings

### B1. Dead "Browse by track" feature (fixed — F1)
- Where: `frontend/src/pages/ProblemBoardPage.tsx` (commit 90aff87).
- Was: track chips (Resume / Hackathon / Learning) read `problem.goal`, a field that existed in no data
  source — not in `backend/app/models.py`, `docs/openapi.json`, `schema.d.ts`, or any seed file. All counts
  were always `0`; selecting any chip always produced an empty board.
- Resolution (design decision by owner): the field is real now, curated manually by admins.
  - Backend: nullable `problems.goal` column (`resume|hackathon|learning|NULL`),
    migration `backend/alembic/versions/0006_problem_goal.py` (defensive, batch-mode, idempotent, downgradable),
    admin-only endpoint `POST /api/admin/problems/{problem_id}/goal` (`body: {"goal": string|null}`; invalid
    values rejected as 422; unknown problem → 404), `goal` exposed on problem list and detail payloads,
    `docs/openapi.json` regenerated.
  - Frontend: types regenerated (`npm run gen:api`), msw mock data labeled, 2 new board tests (chip counts,
    chip click filters and unclick restores).
  - Dev DB `backend/app.db` upgraded in place to `0006_problem_goal`; all 260 problems currently unlabelled
    (NULL) — the owner labels them one by one later.
- Tests: `backend/tests/test_problem_goal.py` (6), migration tests in `tests/test_migrations.py` (3 new; 2
  pre-existing downgrade-offset tests updated to stay accurate now that head moved 0005 → 0006).

### B2. JavaScript `\z` regex escape misbehaviour (fixed)
- Where: `frontend/src/pages/ProblemDetailPage.tsx` (`futureIdeas` extractor).
- Was: `/## (Possible future improvements|Stretch goals)[\s\S]*?(?=\n## |\z)/i`. In JS without the `u` flag,
  `\z` is an **identity escape** matching a literal `z` character, not end-of-string:
  - a ideas/Stretch-goals section containing any `z` truncated the idea list at the first `z`;
  - a section with no following `## Header` and no `z` after it matched **nothing** (ideas rendered empty).
  Verified empirically with node probes reproducing both failure modes.
- Latency note: checked against all 20 seeded briefs that carry such sections in `backend/app.db` — all match
  identically under broken vs fixed regex today (each has a later `## ` header and no `z` inside the section),
  so current visible output was unaffected; fix removes the data-dependence.
- Fix: `(?=\n## |$)`. Regression tests added for both failure modes
  (`frontend/src/pages/ProblemDetailPage.test.tsx`).

### B3. ChatWidget contradictory length message (fixed)
- Where: `frontend/src/components/chat/ChatWidget.tsx`.
- Was: hard guard at `MAX_MESSAGE_LENGTH = 500` but error copy said "under 1000 characters" (the *backend* cap,
  not the one that actually triggers). Fix: copy now says 500.

## E. Remaining known issues (documented, deliberately not fixed)

1. **RateLimiter memory growth** — `backend/app/services/ratelimit.py` keeps one entry per unique IP/user
   forever (prunes only for keys it sees again). Worst case is unbounded memory across many distinct IPs until
   restart. Suggested minimal fix (if wanted): drop entries older than the window on every hit.
2. **Report duplicate race** — concurrent duplicate `POST /api/projects/{id}/report` can surface an unhandled
   `IntegrityError` as 500 instead of a clean 4xx (unique constraint on project+reporter). Client cannot create
   real duplicates; cosmetic severity.
3. **Chat multi-turn context dropped for real providers** — `chat()`'s provider call (`_call_gemini`,
   `_call_anthropic`) sends only the system prompt + last user message; the accepted `messages` history is
   otherwise unused. The mock provider intentionally echoes the last user message (tests encode this). Changing
   the prompt assembly is a provider-behavior design decision, not a bug fix.
4. **Minor frontend notes** — failed message sends can render the user bubble twice on retry (ChatWidget
   entries mutation); unused admin error-message key `repo_already_used_other_problem`; frontend repo-URL
   regex is stricter than the backend's (case-sensitive host), which only ever blocks, never wrongly submits.

## F. Final assessment

The submission/verification pipeline, problem board API, auth/session handling, chat rate limiting, SPA static
serving (path-escape hardened), and migration history are sound: 226 backend + 125 frontend tests, contract
regenerated with the new admin capability, and the dev database fully upgraded. The three defects found were
all fixed with tests; the four remaining items in §E are low-severity, documented, and deliberately left for
follow-up. Next natural step is owner-driven curation: label problems with `/api/admin/problems/{id}/goal`
so the board's track chips come alive on real data.
